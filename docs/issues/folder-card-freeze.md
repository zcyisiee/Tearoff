# 添加文件夹卡片时整个面板卡住

状态：根因已证实，已修复（2026-11-15）。文件夹选择框本身是否正常弹到面板前面，待用户实测。

## 现象

用户点顶栏的“添加文件夹”，面板整个不响应；过一阵自己恢复。

## 根因

所有后端命令当时都是普通的 `#[tauri::command] fn`，Tauri 在**主线程**执行它们。应用启动后第一次读 `~/Desktop` 下的目录很慢，`read_dir` 阻塞期间主线程被占住，窗口不重绘、不收事件。慢的原因推断是系统对“桌面”目录的隐私权限检查（首次还会弹授权框）——这一点是推断，没有单独证实；慢本身和它发生在主线程上是量到的。

证据：加日志后，同一个只有 3 个条目的目录，

- 在终端里 `ls -la` 用时 4ms；
- 在应用里每次启动后第一次 `list_dir`，后端自己量到 838ms（另两次从界面一侧量到 1302ms、1903ms）。



## 修复

- 碰磁盘的 20 个命令改为 `#[tauri::command(async)]`，在工作线程执行。慢读只让那张卡片晚一点出内容，不再冻住面板。
- 顺带把文件夹选择框从前端插件调用改为后端的 `pick_directory`（面板先取焦点、选择框挂为子窗口、期间计入“忙”），避免选择框出现在置顶面板后面。这一条是预防，没有证据表明它曾经发生。

## 类别

主线程上的阻塞调用。同类风险：以后新增的任何读写磁盘、调系统服务的命令。规则写在 `docs/reference/contracts.md` 的“命令的线程”。

## 未覆盖

没有自动化回归：需要一个“慢目录”才能复现。现在靠日志守——`list_dir` 磁盘耗时超过 100ms、界面线程停顿超过 1.5 秒都会记 WARN。
